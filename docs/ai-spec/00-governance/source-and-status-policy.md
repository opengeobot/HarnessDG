# 事实源、状态与证据规则

> 状态：`DRAFT`

## 1. 规范事实优先级

发生冲突时按以下优先级处理：

1. 当前任务已确认的目标、范围和验收标准；
2. Accepted ADR；
3. 已发布的 OpenAPI、MCP、事件 Schema、Flyway 和状态机契约；
4. 已确认的 AI 可执行需求；
5. 产品设计说明书；
6. 当前代码和测试；
7. 历史任务勾选、实现状态快照和完成报告。

高优先级内容不是自动覆盖低优先级内容的许可证。发现冲突后必须：

1. 建立冲突 ID；
2. 标出受影响需求和交付物；
3. 判断是新需求、文档漂移、契约错误还是实现偏离；
4. 由有权决策者确认；
5. 在同一变更中同步所有受影响事实。

涉及技术路线、模块边界、事实源、身份、安全模型或发布语义的变化必须新增 ADR。

## 2. 规范文档与证据文档分离

| 类型 | 示例 | 能否定义目标行为 |
| --- | --- | --- |
| 规范 | 已确认需求、ADR、OpenAPI、状态机 | 可以 |
| 实现 | Java/TypeScript、SQL、Compose | 只能实现规范 |
| 验证 | 测试、Verify 输出、截图、Trace、性能报告 | 只能证明覆盖范围内的行为 |
| 历史 | dated snapshot、完成报告、任务勾选 | 不能；只记录当时声明 |

实现状态快照必须带日期和 Commit SHA。没有 Commit SHA 的快照只能作为线索，不能作为可复现证据。

## 3. 需求状态

仅允许使用以下状态：

| 状态 | 含义 |
| --- | --- |
| `OPEN` | 存在影响行为的未决问题 |
| `PROPOSED` | 已起草，但尚未获得产品确认 |
| `READY` | 输入、规则、权限、错误、审计和验收均已明确，可以实施 |
| `IN_PROGRESS` | 正在实现 |
| `IMPLEMENTED_UNVERIFIED` | 有实现，但证据未达到最低等级 |
| `VERIFIED` | 证据达到需求声明的最低等级且追踪闭环 |
| `BLOCKED` | 外部依赖或决策阻止继续，且已记录解除条件 |
| `SUPERSEDED` | 被新需求或 ADR 替代，并保留替代链接 |

禁止使用没有验收含义的 `done`、`mostly done`、`基本完成` 或 `已落地`。

## 4. 证据等级

| 等级 | 证据 | 可以证明 | 不能证明 |
| --- | --- | --- | --- |
| `E0` | 文档、勾选、代码注释 | 有过设计或声明 | 代码存在或行为正确 |
| `E1` | 静态扫描、编译、Lint、Schema lint | 结构和语法满足检查 | 运行时业务行为 |
| `E2` | 单元/组件测试 | 隔离规则或组件行为 | 真实数据库和跨系统链路 |
| `E3` | PostgreSQL/Testcontainers、契约和 Adapter 集成测试 | 真实协议或持久化行为 | 完整部署与用户旅程 |
| `E4` | 全栈 Compose/E2E、浏览器、MCP 客户端验证 | 部署基线中的完整用户旅程 | 生产容量和长期稳定性 |
| `E5` | 性能、安全、恢复演练和持续观测报告 | 指定环境下的非功能目标 | 未测试环境的结果 |

每条需求必须声明最低证据等级。广泛需求不能由狭窄证据支持，例如：

- 401/403 只能证明拒绝路径，不能证明有权限主体的成功路径；
- Controller Mock 测试不能证明数据库权限下推；
- Compose 服务 Healthy 不能证明 JWT 轮换和重放检测；
- 页面文件存在或构建成功不能证明交互、权限、i18n 和可访问性；
- 一次运行成功不能证明故障恢复、并发或幂等。

## 5. 证据记录

验收记录至少包含：

```yaml
requirementId: REQ-...
commitSha: ...
environment:
  os: ...
  runtime: ...
  composeProfiles: [...]
command: ...
startedAt: ...
finishedAt: ...
result: PASS | FAIL | SKIP
artifacts:
  - path-or-report
coverage:
  - scenario-id
limitations:
  - ...
```

`SKIP` 永远不折算为 `PASS`。历史日志若无法关联 Commit SHA、命令和环境，不得用于把需求标成
`VERIFIED`。

## 6. AI 修改状态的权限

AI 可以：

- 将 `READY` 改为 `IN_PROGRESS`；
- 在实现和低等级证据完成后改为 `IMPLEMENTED_UNVERIFIED`；
- 附加实际运行证据。

AI 不得：

- 自行把 `OPEN` 或 `PROPOSED` 改为 `READY`；
- 仅凭代码存在把需求改为 `VERIFIED`；
- 替用户决定产品范围、组织模型、审批语义或风险接受；
- 删除失败或 SKIP 记录来获得绿色状态。
